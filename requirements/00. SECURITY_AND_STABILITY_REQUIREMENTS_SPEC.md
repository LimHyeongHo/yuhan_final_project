# 보안·거래 안정성 개선 요구사항 명세서

## 1. 문서 정보

| 항목 | 내용 |
|---|---|
| 문서 버전 | 1.0 |
| 작성일 | 2026-09-05 |
| 기준 문서 | `TEAM_FEEDBACK_VERIFICATION_REPORT.md` |

| 문서 목적 | 검증된 결함을 구현·테스트 가능한 요구사항과 인수 기준으로 정의 |

## 2. 목표

본 개선의 목표는 다음과 같다.

1. 서버를 신뢰 가능한 유일한 인증·인가 판단 주체로 만든다.
2. 상품, 결제, 참여, 회원 상태 사이의 데이터 정합성을 보장한다.
3. 외부 결제·블록체인 장애가 핵심 조회 기능을 중단시키지 않게 한다.
4. 현재 확인된 UI 잠김과 미구현 동작을 사용자가 예측 가능한 방식으로 정리한다.
5. 자동화된 보안·동시성 테스트를 통과하기 전에는 외부 배포하지 않는다.

## 3. 범위

### 3.1 포함 범위

- HTTP 세션 로그인·로그아웃 및 역할 기반 접근 제어
- PKI 인증서 발급·폐기·재발급
- 회원 탈퇴와 탈퇴 판매자의 상품 처리
- 상품 등록·수정·삭제·참여·취소
- 결제 완료 후 취소·환불
- 상품 모집 상태와 정원 동시성
- 블록체인 기록, 조회, Nonce 관리, 실패 복구
- 판매자 프로필·후기·검색·공유 UI
- 채팅방 나가기·메시지 전송 취소·상품 바로가기
- 비밀정보 관리와 보안 테스트

### 3.2 제외 또는 별도 관리 범위

- Naver 쇼핑 검색 API 대체 공급자 선정은 별도 요구사항으로 관리한다.
- 관심 상품 하트 기능은 이미 구현되어 있으므로 신규 개발 대상에서 제외하고 회귀 테스트만 수행한다.
- 관리자 프로필은 현재 관리자 대시보드에 연결되어 있으므로 신규 개발 대상에서 제외하고 회귀 테스트만 수행한다.
- 피드백의 `-10,000원 복구` 코드는 현재 브랜치에 존재하지 않으므로 해당 산술 로직 수정이 아니라 안전한 시뮬레이션·복구 기능을 새로 정의한다.

## 4. 정책 가정 및 확정 필요 사항

다음 정책은 구현 기준으로 제안한다. 팀 또는 서비스 책임자가 변경하면 관련 요구사항과 테스트도 함께 변경해야 한다.

1. 탈퇴 계정은 거래 감사 이력 보존을 위해 물리 삭제 대신 `WITHDRAWN` 상태로 비활성화한다.
2. 판매자 탈퇴 시 해당 판매자의 `OPEN` 상품은 즉시 `SELLER_WITHDRAWN` 또는 동등한 종료 상태로 전환한다.
3. 결제 완료 후 사용자 변심 취소는 모집 완료·정산 시작 전까지만 허용한다.
4. 가격 인하는 모집 중이고 완료 결제가 한 건도 없을 때만 허용한다.
5. 목표 인원 변경값은 현재 참여 인원보다 작을 수 없다.
6. 채팅 메시지 전송 취소는 실제 행 삭제 대신 삭제 표식을 남기는 소프트 삭제 방식으로 처리한다.

## 5. 역할 및 접근 권한 기준

### 5.1 역할

| 역할 | 설명 |

| ANONYMOUS | 로그인하지 않은 사용자 |
| ROLE_BUYER | 상품 조회·결제·참여·후기 작성 사용자 |
| ROLE_SELLER_PENDING | 판매자 승인 대기 사용자 |
| ROLE_SELLER | 본인 상품과 판매 관련 기능을 관리하는 사용자 |
| ROLE_ADMIN | 관리자 기능과 보안 시뮬레이션을 수행하는 사용자 |
| SYSTEM | 서버 내부 스케줄러·인증기관·백그라운드 작업 |

## 6. 보안 및 인증 요구사항

### SEC-RQ-001 기본 차단형 보안 정책

- 우선순위: P0
- 요구사항:
  - Spring Security는 기본적으로 모든 요청에 인증을 요구해야 한다.
  - 로그인, 회원가입 준비, 공개 상품 조회처럼 명시적으로 정의한 엔드포인트만 `permitAll`로 허용해야 한다.
  - 역할 제한은 URL뿐 아니라 서비스 계층의 중요 변경 작업에도 적용해야 한다.
- 인수 기준:
  1. 익명 사용자가 보호 API를 호출하면 HTTP 401을 받는다.
  2. 로그인했지만 역할이 부족하면 HTTP 403을 받는다.
  3. 권한 오류가 HTTP 500으로 변환되지 않는다.
  4. 전체 API 권한 매트릭스 자동화 테스트가 통과한다.
- 추적: SEC-03, SEC-04, SELL-02 및 추가 발견 1~4

### SEC-RQ-002 서버 로그아웃

- 우선순위: P0
- 요구사항:
  - 로그아웃 API는 현재 HTTP 세션을 무효화하고 JSESSIONID 쿠키를 만료시켜야 한다.
  - 프론트는 서버 로그아웃 성공 또는 이미 만료된 세션 응답을 확인한 후 로컬 인증 정보를 제거해야 한다.
  - 수동 로그아웃은 정책상 인증서를 폐기하지 않는다.
- 인수 기준:
  1. 로그인 후 `/api/member/info`는 200을 반환한다.
  2. 로그아웃 후 같은 쿠키로 호출하면 401을 반환한다.
  3. 뒤로가기나 localStorage 복원으로 보호 화면·API에 재진입할 수 없다.
- 추적: SEC-01

### SEC-RQ-003 회원가입 역할 서버 결정

- 우선순위: P0
- 요구사항:
  - 회원가입 요청 DTO는 `ROLE_ADMIN`을 포함한 최종 권한 문자열을 받지 않아야 한다.
  - 일반 가입은 서버에서 `ROLE_BUYER`, 판매자 신청은 `ROLE_SELLER_PENDING`으로 결정한다.
  - `ROLE_SELLER` 승격은 관리자 승인 API로만 가능해야 한다.
  - `ROLE_ADMIN` 생성·변경은 공개 회원가입과 분리된 운영 절차로만 허용한다.
- 인수 기준:
  1. 요청에 `ROLE_ADMIN` 또는 임의 role을 추가해도 관리자 계정이 생성되지 않는다.
  2. 허용되지 않은 역할 요청은 무시하지 않고 400으로 거부하거나 DTO 역직렬화 단계에서 차단한다.
  3. 판매자 승인 이력이 감사 로그에 남는다.
- 추적: SEC-02

### SEC-RQ-004 상품 변경 권한과 소유권

- 우선순위: P0
- 요구사항:
  - 상품 생성은 활성 `ROLE_SELLER` 세션만 허용한다.
  - 상품 수정·삭제는 상품의 `sellerEmail`과 세션 사용자가 일치할 때만 허용한다.
  - 관리자는 별도의 관리자 API를 통해 관리 작업을 수행한다.
  - sellerEmail, sellerId, currentCount, status, txHash 등 서버 관리 필드는 클라이언트 바인딩 대상에서 제외한다.
- 인수 기준:
  1. 익명 생성·수정·삭제 요청은 401이다.
  2. 구매자 요청과 타 판매자 요청은 403이다.
  3. 본인 판매자는 허용 필드만 수정할 수 있다.
  4. 요청 FormData에 sellerEmail·status 등을 삽입해도 저장값을 변경할 수 없다.
- 추적: SEC-03 및 추가 발견 1~2

### SEC-RQ-005 CA·PKI 관리 API 보호

- 우선순위: P0
- 요구사항:
  - `/api/ca/issue`, `/api/ca/revoke` 같은 원시 CA API는 외부 공개 라우트에서 제거하거나 SYSTEM/ADMIN 전용으로 제한한다.
  - 사용자 인증서 폐기는 인증된 본인 세션 또는 권한 있는 관리자만 수행한다.
  - 클라이언트가 보낸 deviceId·serialNumber만으로 소유권을 인정하지 않는다.
  - 폐기 정보는 DB에 영속화하고 서버 재시작 후에도 유지한다.
- 인수 기준:
  1. 익명 폐기 요청은 401이다.
  2. 타인 인증서 폐기 요청은 403이다.
  3. 서버 재시작 후에도 폐기 인증서는 로그인 검증을 통과하지 못한다.
- 추적: SEC-04 및 추가 발견 6

### SEC-RQ-006 CSRF 방어

- 우선순위: P0
- 요구사항:
  - 쿠키 기반 세션을 사용하는 모든 상태 변경 요청에 CSRF 보호를 적용한다.
  - SPA는 서버가 발급한 CSRF 토큰을 지정 헤더로 전송한다.
  - CORS와 CSRF를 서로 대체 가능한 방어로 취급하지 않는다.
- 인수 기준:
  1. 올바른 세션 쿠키만 있고 CSRF 토큰이 없는 외부 출처 변경 요청은 403이다.
  2. 정상 프론트 요청은 CSRF 토큰과 함께 성공한다.
- 추적: 추가 발견 5

### SEC-RQ-007 비밀정보 관리

- 우선순위: P0
- 요구사항:
  - DB 비밀번호, 결제·본인인증 API Secret, 블록체인 개인키, 외부 노드 키를 소스 및 공유 문서에 저장하지 않는다.
  - 환경 변수 또는 배포 환경의 Secret Manager로 주입한다.
  - 노출 가능성이 있는 현재 키는 폐기하고 재발급한다.
  - 로그와 오류 응답에 비밀값이 포함되지 않아야 한다.
- 인수 기준:
  1. Git 추적 파일 비밀 검색에서 실제 키가 발견되지 않는다.
  2. 키가 없는 환경에서는 안전한 시작 실패 또는 해당 기능 비활성 상태가 명확히 기록된다.
- 추적: 추가 발견 7

## 7. 회원 생명주기 요구사항

### MEM-RQ-001 회원 탈퇴 원자성

- 우선순위: P1
- 요구사항:
  - 탈퇴는 인증서 폐기, 인증서 세션 종료, 계정 비활성화, 관련 상품 처리까지 하나의 명확한 업무 트랜잭션으로 수행한다.
  - 거래·결제·후기 감사 데이터는 보존하되 개인 표시 정보는 정책에 따라 익명화한다.
  - 중간 실패 시 일부 데이터만 삭제된 상태가 남지 않아야 한다.
- 인수 기준:
  1. 인증서 타이머 잔여 시간과 관계없이 탈퇴가 같은 결과를 낸다.
  2. Participation·Payment·Scrap이 존재하는 계정도 500 없이 정책대로 처리된다.
  3. 성공 후 기존 세션은 401이고 재로그인은 거부된다.
  4. 동일 요청 재시도는 멱등하게 처리된다.
- 추적: SEC-05

### MEM-RQ-002 탈퇴 판매자 거래 차단

- 우선순위: P0
- 요구사항:
  - 판매자 탈퇴 또는 비활성화 시 해당 판매자의 모집 중 상품을 즉시 거래 불가 상태로 변경한다.
  - 상품 조회, 결제 준비, 참여, 채팅방 생성 각각에서 판매자 활성 상태를 서버가 검증한다.
  - 이미 완료된 결제의 환불·정산 정책을 별도 상태로 처리한다.
- 인수 기준:
  1. 탈퇴 판매자 상품의 결제 준비·참여·신규 채팅 요청은 409 또는 정책상 오류로 거부된다.
  2. 화면의 참여·문의 버튼은 비활성화되고 사유를 표시한다.
  3. 기존 거래·후기 이력은 조회 정책에 따라 유지된다.
- 추적: SELL-01

### MEM-RQ-003 재발급 실패 UI 초기화

- 우선순위: P2
- 요구사항:
  - 인증서 재발급 실패 후 이메일을 변경하고 본인인증부터 다시 시작할 수 있는 `처음부터 다시` 동작을 제공한다.
  - 초기화 시 isVerified, needsReissue, regCi, privateKey 참조, 오류 상태를 초기화한다.
- 인수 기준:
  1. 재발급 실패 직후 새로고침 없이 이메일 입력이 가능하다.
  2. 계정 변경 후 이전 계정의 CI·개인키 상태가 요청에 재사용되지 않는다.
- 추적: SEC-06

## 8. 공동구매·결제 요구사항

### PRD-RQ-001 사용자별 참여 취소

- 우선순위: P1
- 요구사항:
  - 취소 API는 인증된 구매자의 본인 Participation을 대상으로 해야 한다.
  - Product.currentCount, Participation 상태, Payment 상태를 한 트랜잭션에서 일치시킨다.
  - 단순 productId만으로 임의 인원 감소를 허용하지 않는다.
- 인수 기준:
  1. 취소 후 currentCount가 정확히 1 감소한다.
  2. 마이페이지에는 `취소됨` 상태가 표시되거나 정책에 따라 활성 목록에서 제외된다.
  3. 중복 취소는 인원수를 추가 감소시키지 않는다.
  4. 타인의 참여 건은 취소할 수 없다.
- 추적: GP-01 및 추가 발견 4

### PAY-RQ-001 결제 취소·환불

- 우선순위: P1
- 요구사항:
  - 결제 완료 건 취소는 결제 공급자의 공식 취소 API를 호출해야 한다.
  - Payment는 최소 `PENDING`, `DONE`, `CANCEL_REQUESTED`, `CANCELED`, `REFUND_FAILED` 상태를 구분한다.
  - 환불 성공 전에는 Participation과 currentCount를 확정적으로 취소 처리하지 않는다.
  - 콜백과 재시도는 orderId/paymentKey 기준으로 멱등해야 한다.
- 인수 기준:
  1. 결제 공급자 취소 성공 후 Payment·Participation·Product 값이 일치한다.
  2. 공급자 취소 실패 시 참여 인원은 유지되고 사용자가 재시도 가능한 상태를 확인한다.
  3. 정산 시작 후 사용자 자가 취소는 정책에 따라 거부된다.
- 추적: GP-02

### PRD-RQ-002 정원 달성 즉시 모집 차단

- 우선순위: P1
- 요구사항:
  - currentCount가 targetCount에 도달하면 즉시 `FULL` 또는 승인된 동등 상태로 전환한다.
  - FULL 상태에서는 추가 결제 준비·참여 요청을 서버가 거부한다.
  - 프론트 목록과 상세는 `모집 완료`를 표시하고 참여 버튼을 비활성화한다.
- 인수 기준:
  1. 마지막 참여 성공 응답 직후 상품 상태가 OPEN이 아니다.
  2. 새로고침 없이 상세 화면 버튼과 상태가 갱신된다.
  3. 100% 상품에 대한 추가 결제 준비는 거부된다.
- 추적: GP-03

### PRD-RQ-003 정원 동시성 제어

- 우선순위: P1
- 요구사항:

- 인수 기준:
  1. 잔여 1석에 동시 요청을 보내도 성공 Participation은 하나뿐이다.
  2. 결제만 승인되고 참여가 거절되는 고아 결제가 발생하면 자동 환불 또는 보상 처리가 실행된다.

### PRD-RQ-004 가격·목표 인원 수정 정책

  3. targetCount를 currentCount 미만으로 변경할 수 없다.
- 추적: GP-04

## 10. 블록체인 요구사항

### BC-RQ-001 Nonce 직렬화

- 우선순위: P1
- 요구사항:
  - 동일 송신 지갑의 트랜잭션 생성·전송은 단일 직렬 큐 또는 원자적 Nonce 관리자를 통해 처리한다.
  - 초기 Nonce는 `PENDING` 기준으로 조회한다.
  - `nonce too low`, `replacement transaction underpriced`, 네트워크 오류를 분류해 제한적으로 재시도한다.
- 인수 기준:
  1. 여러 상품을 동시에 등록해도 서로 다른 연속 Nonce가 배정된다.
  2. 성공 건의 txHash가 각 상품에 정확히 저장된다.
  3. 재시작 후에도 이미 전송된 Nonce와 충돌하지 않는다.
- 추적: BC-02

### BC-RQ-002 비동기 작업 상태와 재시도

- 우선순위: P1
- 요구사항:
  - 블록체인 기록 상태를 최소 `QUEUED`, `SUBMITTED`, `CONFIRMED`, `FAILED_RETRYABLE`, `FAILED_FINAL`로 저장한다.
  - 오류를 로그만 남기고 삼키지 않는다.
  - 재시도 횟수와 마지막 오류를 관리자가 확인할 수 있어야 한다.
- 인수 기준:
  1. txHash가 없는 이유가 단순 PENDING인지 최종 실패인지 API로 구분된다.
  2. 재시도 가능한 실패는 설정된 횟수만큼 자동 재처리된다.
- 추적: BC-02

### BC-RQ-003 외부 노드 타임아웃과 조회 격리

- 우선순위: P1
- 요구사항:

  - 상품 DB 상세 조회는 블록체인 노드 가용성과 독립적으로 성공해야 한다.

## 13. 비기능 요구사항

### NFR-001 오류 응답 표준화

- 400, 401, 403, 404, 409, 500을 원인에 맞게 구분한다.
- 모든 오류 응답은 `code`, `message`, `timestamp`, `path`를 포함한다.
- 서버 내부 예외 메시지, SQL, 키, 외부 공급자 원문 비밀정보를 클라이언트에 노출하지 않는다.

### NFR-002 감사 로그

- 역할 승인, 상품 변경·삭제, 회원 탈퇴, 환불, 인증서 폐기, 시뮬레이션, 블록체인 재시도는 감사 로그를 남긴다.
- 로그는 수행자, 대상, 작업, 결과, 시각, 요청 추적 ID를 포함한다.

### NFR-003 멱등성

- 로그아웃, 회원 탈퇴, 결제 콜백, 환불, 참여 취소, 인증서 폐기, 시뮬레이션 복구는 안전하게 재시도할 수 있어야 한다.

### NFR-004 성능과 타임아웃

- 공개 상품 기본 조회는 외부 API·블록체인 응답을 기다리지 않는다.
- 모든 외부 HTTP/RPC 호출은 연결 및 응답 타임아웃을 설정한다.
- 백그라운드 작업 상태 조회는 DB 기반으로 제공한다.

## 14. 구현 순서 및 의존성

| 단계 | 요구사항 | 선행 조건 | 완료 기준 |
|---|---|---|---|
| 1 | SEC-RQ-001~007 | 없음 | 익명·역할 공격 테스트 차단 |
| 2 | MEM-RQ-001~002, UI-RQ-001 | 1단계 | 탈퇴·세션·판매자 상태 정합성 확보 |
| 3 | PRD-RQ-001~005, PAY-RQ-001 | 1~2단계 | 참여·결제·정원 동시성 테스트 통과 |
| 4 | SIM-RQ-001~002, BC-RQ-001~003 | 1단계 | 다중 트랜잭션·노드 장애 테스트 통과 |
| 5 | MEM-RQ-003, UI-RQ-002~006, CHAT-RQ-001~003 | 1~4단계 관련 API | 사용자 인수 테스트 통과 |

보안 P0 완료 전에는 UI 편의 기능보다 서버 권한 경계 수정이 우선이다.

## 15. 릴리스 인수 기준

다음 조건을 모두 충족해야 보안·안정성 개선 릴리스를 완료로 판정한다.

1. P0 요구사항과 자동화 테스트가 모두 통과한다.
2. 익명·BUYER·SELLER·ADMIN 권한 매트릭스에서 예상 외 2xx 응답이 없다.
3. 로그아웃 후 기존 쿠키 재사용이 차단된다.
4. role 위조 가입과 타인 상품 변경 공격이 차단된다.
5. 참여·취소·환불 후 Product, Participation, Payment 데이터가 일치한다.
6. 잔여 1석 동시 결제 테스트에서 초과 참여가 발생하지 않는다.
7. 탈퇴 판매자 상품의 참여·결제·신규 채팅이 불가능하다.
8. 10건 이상의 동시 블록체인 등록에서 Nonce 충돌이 발생하지 않는다.
9. 블록체인 노드 장애 중에도 상품 기본 상세가 정상 표시된다.
10. 비밀정보 검사에서 실제 자격 증명이 발견되지 않는다.
11. 기존 관심 상품 하트와 관리자 프로필 링크 회귀 테스트가 통과한다.
