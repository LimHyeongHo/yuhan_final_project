# 02. 요구사항 명세서 (Requirements)

- 문서 기준일: 2026-10-21
- 구현 상태: `완료`, `부분`, `미구현`, `미검증`
- 우선순위: `MUST`, `SHOULD`, `COULD`, `WON'T`

## 1. 액터와 권한

| 액터/상태 | 시스템 값 | 주요 권한 |
|---|---|---|
| 구매자 | `ROLE_BUYER` | 상품 조회, 스크랩, 결제/참여/취소, 채팅, 후기, 문의 |
| 판매자 승인 대기 | `ROLE_SELLER_PENDING` | 구매자 기능 이용, 판매자 전용 기능은 승인 전 제한 |
| 판매자 | `ROLE_SELLER` | 상품 등록/수정/삭제, 주문 및 참여자 확인, 채팅, 분석, 정산/출금 |
| 관리자 | `ROLE_ADMIN` | 판매자 승인, 회원·상품·신고·출금 관리, 보안 로그·시뮬레이션 |

`SELLER_PENDING`은 별도 사용자 유형이 아니라 판매자 승인 절차의 중간 상태다. B2B 제휴사용 별도 액터와 권한은 현재 구현되지 않았다.

## 2. 기능 우선순위와 현재 상태

MoSCoW는 중요도이며, 구현 상태와 같은 개념이 아니다.

| 우선순위 | 기능 | 현재 상태 |
|---|---|---|
| MUST | PortOne CI 본인인증, 회원가입, 1인 1활성 계정 | 완료(PoC/테스트 채널 포함) |
| MUST | 비밀번호 + RSA-OAEP 기기 챌린지 로그인 | 완료 |
| MUST | 상품 등록·수정·삭제, 구매자 참여 | 완료 |
| MUST | Toss Payments 결제 준비·승인·취소·자동 환불 | 완료 |
| MUST | 구매/판매 진행 상태와 이력 조회 | 완료 |
| MUST | DB–Sepolia 상품 해시 무결성 검증 | 완료(PoC) |
| SHOULD | 구매자–판매자 1:1 WebSocket 채팅·알림 | 완료 |
| SHOULD | 외부 도서/상품 검색·공식 정가 비교 | 부분 |
| SHOULD | 스크랩, 후기, 문의, 신고 | 완료 |
| SHOULD | 판매자 정산 계좌·출금 신청, 관리자 처리 | 완료 |
| COULD | AI 개인화 추천/상품 작성 보조 | 미구현 |
| COULD | 도서 바코드 스캔 | 미구현 |
| WON'T | 전국 대학·B2B 배송/물류 트래킹 | 현 단계 제외 |

## 3. 기능 요구사항

### 3.1 인증·계정

| ID | 요구사항 | 인수 기준 | 상태 |
|---|---|---|---|
| AUTH-01 | 회원가입 전 PortOne 본인인증 결과를 서버 API로 재확인한다. | 검증 상태가 `VERIFIED`인 경우에만 CI를 사용한다. | 완료 |
| AUTH-02 | 활성 계정의 CI 중복을 차단한다. | 다른 활성 계정에 같은 CI hash가 있으면 가입을 거부한다. | 완료 |
| AUTH-03 | 가입 시 브라우저에서 RSA-OAEP 키 쌍을 생성하고 공개키를 서버에 등록한다. | 개인키는 IndexedDB에, 공개키·인증서 정보는 DB에 저장한다. | 완료 |
| AUTH-04 | 로그인은 본인인증 CI, 비밀번호, 기기 개인키 보유 증명을 모두 요구한다. | RSA-OAEP 암호화 nonce를 복호화해 반환한 뒤 HTTP Session을 생성한다. | 완료 |
| AUTH-05 | 인증서 만료·폐기·재발급을 처리한다. | 만료/폐기 인증서로 로그인을 거부하고 재발급 흐름을 제공한다. | 완료(PoC) |
| AUTH-06 | 회원은 닉네임·비밀번호를 변경하고 탈퇴할 수 있다. | 탈퇴 시 행을 삭제하지 않고 `WITHDRAWN`으로 전환한다. | 완료 |
| AUTH-07 | 판매자 신청은 관리자 승인 후 판매 권한을 받는다. | `ROLE_SELLER_PENDING` → `ROLE_SELLER` 전환은 관리자 API에서만 수행한다. | 완료 |

> 예외: 정해진 관리자·시연용 테스트 계정은 이메일/비밀번호 로그인 엔드포인트를 사용한다. 일반 가입 계정은 해당 목록에 포함되지 않는다.

### 3.2 상품·공동구매

| ID | 요구사항 | 인수 기준 | 상태 |
|---|---|---|---|
| PRD-01 | 승인된 판매자는 도서 또는 일반 상품을 등록한다. | 서버가 판매자 세션을 확인하고 `sellerEmail`, `OPEN`, `currentCount=0`을 설정한다. | 완료 |
| PRD-02 | 판매자는 `OPEN` 상태의 본인 상품을 수정/삭제한다. | 권한·소유자·상태를 검사한다. 가격/ISBN 변경 시 해시를 다시 기록한다. | 완료 |
| PRD-03 | 구매자는 모집 중인 상품에 1회 참여한다. | 중복 참여, 마감, 정원 초과, 판매자 탈퇴, 상품 위변조(FORGED)를 서버에서 차단한다. 자기 상품 참여는 상품 상세 화면에서만 차단한다(서버 검증 없음). | 완료 |
| PRD-04 | 참여 인원 갱신은 동시성을 제어한다. | `PESSIMISTIC_WRITE` 락 범위에서 정원 검사와 증감을 수행한다. | 완료 |
| PRD-05 | 목표 인원 달성 또는 마감 시각 도래 시 상태를 전환한다. | 마지막 참여 확정 시 즉시 `CLOSED_SUCCESS`로 전환하고, 마감 시각까지 미달이면 스케줄러가 `CLOSED_FAIL`로 전환한다. | 완료 |
| PRD-06 | 구매자는 상품을 스크랩하고 본인 목록에서 조회/해제한다. | 계정–상품 조합을 저장한다. | 완료 |
| PRD-07 | 도서/상품 검색과 공식 정가 비교를 제공한다. | Naver·Kakao·Google 연동 실패를 구분하고, 가격 검증 결과를 표시한다. | 부분 |

### 3.3 결제·환불·정산

| ID | 요구사항 | 인수 기준 | 상태 |
|---|---|---|---|
| PAY-01 | 결제 전 서버가 상품 가격과 상태를 검증하고 `PENDING` 기록을 생성한다. | 클라이언트가 보낸 금액을 신뢰하지 않는다. | 완료 |
| PAY-02 | Toss Payments 성공 콜백에서 결제를 승인한다. | `PENDING → APPROVED → DONE` 순서로 결제와 참여를 확정한다. | 완료 |
| PAY-03 | 승인 응답 유실 시 Toss 실제 상태를 재조회한다. | 재시도가 중복 승인으로 잘못 판정되지 않도록 멱등적으로 처리한다. | 완료 |
| PAY-04 | Toss 승인 후 참여 확정이 실패하면 자동 환불한다. | `CANCEL_REQUESTED → CANCELED/REFUND_FAILED`를 기록한다. 취소 전 Toss 실제 상태를 재조회하고, `REFUND_FAILED`는 구매자 재취소 또는 콜백 재호출 시 재시도한다. | 완료 |
| PAY-05 | 구매자의 참여 취소는 결제 환불과 참여 정리를 함께 처리한다. | 모집 중(`OPEN`) 상품만 취소할 수 있다. 상품 락 안에서 `CANCEL_REQUESTED`를 선점해 중복 취소를 막고, 환불 성공 후에만 참여 행과 현재 인원을 줄인다. | 완료 |
| PAY-06 | 상품 삭제·모집 실패·판매자 탈퇴로 종료된 공동구매의 결제를 자동 환불한다. | `PaymentRefundScheduler`가 1분마다 `DONE`과 10분 이상 지난 `APPROVED`·`CANCEL_REQUESTED` 결제를 찾아 환불하고, 실패 시 `REFUND_FAILED`를 기록한다. | 완료 |
| SET-01 | 판매자는 정산 계좌를 등록하고 출금을 신청한다. | 출금 가능 금액(`CLOSED_SUCCESS` 상품의 `DONE` 결제 합계 − 신청·완료된 출금 합계)과 계좌 정보를 검증해 `REQUESTED`를 생성한다. 계좌 행 락으로 중복 신청을 막는다. | 완료 |
| SET-02 | 관리자는 출금 신청을 승인 또는 거절한다. | `COMPLETED`/`REJECTED` 상태·거절 사유·처리 시각을 저장한다. 실제 송금은 시스템 밖에서 수행한다. | 완료 |

### 3.4 블록체인·무결성

| ID | 요구사항 | 인수 기준 | 상태 |
|---|---|---|---|
| BC-01 | 상품 등록 커밋 후 해시를 비동기로 Sepolia에 전송한다. | DB 커밋 이전에 외부 네트워크를 호출하지 않는다. | 완료 |
| BC-02 | 해시 대상은 `productId`, `isbn`, `price`로 고정한다. | DB와 검증 코드가 같은 정규화 규칙을 사용한다. | 완료 |
| BC-03 | 전송·채굴·RPC 실패를 상태와 재시도 횟수로 관리한다. | `QUEUED/SUBMITTED/CONFIRMED/FAILED_RETRYABLE/FAILED_FINAL`을 구분한다. | 완료 |
| BC-04 | 상품 상세 검증 시 DB 해시와 온체인 해시를 비교한다. | 불일치 시 `FORGED`/위변조 경고, 장애 시 `UNAVAILABLE`을 구분한다. | 완료 |
| BC-05 | 컨트랙트 기록 권한과 덮어쓰기를 제한한다. | 인가된 주소만 기록하고 변경 이력을 추가 방식으로 보존한다. | 미구현 |

| NFR-02 | 인증/인가 | API 인증은 HTTP Session과 기본 차단 인터셉터를, 관리자 인가는 전용 인터셉터를 사용한다. | 완료 |

| NFR-04 | 장애 복구 | 결제 외부 호출에 타임아웃·실제 상태 재조회·환불 재시도를 적용한다. | 완료 |
| NFR-05 | 사용성 | 일반 API 오류는 현재 화면의 메시지/모달로 안내한다. | 부분 |
| NFR-06 | 예외 UX | 외부 결제 리다이렉트 실패는 `/payment/fail` 전용 페이지로 안내한다. | 완료 |

| NFR-10 | 테스트 | 메인 병합 전 프런트·백엔드 자동 테스트를 통과한다. | CI 미구현, 현재 프런트 1개 테스트 실패 |

## 5. 정책·해석 주의사항

- PKI는 로그인 기기 인증에 사용하며 결제 금액을 애플리케이션 수준에서 별도 암호화하지 않는다. 결제 금액 무결성은 서버 재계산과 Toss 승인 금액 대조로 확보한다.
- 관리자는 실시간 채팅의 일반 참여자가 아니다. 다만 신고·로그 관리 범위에서 관련 메타데이터를 처리할 수 있다.
- 별도 오류 페이지를 완전히 금지하지 않는다. 결제처럼 외부 리다이렉트가 필요한 흐름은 성공/실패 페이지를 사용한다.
- 재고·시세 그래프는 현재 완성된 구매자 기능으로 보지 않는다. 외부 검색, 공식 정가, 자체 가격 변경 이력을 명확히 구분한다.
